Trading Platform Blueprint

Sprint 8 · Enterprise Trading Platform

System architecture & order lifecycle

Seven services split across three concerns: a JWT-issuing auth service that is the only thing to ever see a password, a synchronous REST path for accounts and orders, and an asynchronous Kafka path that fills orders and rebuilds a DuckDB analytics warehouse in the background. Everything inside the dashed boundary is one Docker Compose network; the browser and the Fauxnance quote provider sit outside it.

Order lifecycle, start to finish

  1. 01 Register & sign in. The browser fetches the Auth Service's RSA public key, seals the credentials with a fresh AES-256-GCM key wrapped in RSA-OAEP, and posts { request: "<ciphertext>" } — the plaintext password never appears in the request body. Login returns a 15-minute access token plus an HttpOnly refresh_token cookie.
  2. 02 Place an order. The frontend calls POST /api/v1/orders on the Trade API with the bearer token. Trade API verifies the JWT's signature and issuer locally — no call back to Auth — writes the order as NEW in trading.orders, and publishes ORDER_PLACED to the Kafka orders topic.
  3. 03 Fill or reject. The Executor consumes orders (partitioned by accountId for strict per-account ordering), fetches a quote from Fauxnance, and in one transaction moves the order to FILLED, debits cash with an optimistic version lock, and upserts the holding. It publishes ORDER_FILLED or ORDER_REJECTED to trade-events. A background MarketDataPoller rescues any order still stuck at NEW.
  4. 04 Rebuild analytics. The Executor's EtlStartupRunner keeps a Python subprocess alive that re-reads trading_system_db roughly every 45 seconds and rewrites analytics.duckdb (a star schema of accounts, dates, instruments, and fact trades) on a volume shared with the frontend, which queries the file directly for /analytics — no API hop.

Services at a glance

Frontend

:5000

Flask · Python 3.11

Registration, login, dashboard and the analytics view. Stores only the access token client-side; the refresh token never leaves an HttpOnly cookie.

Auth Service

:3000

NestJS · Node 20

The only service that touches a password. bcrypt cost 12, RSA-4096 sealed transport, non-rotating 7-day refresh tokens stored as SHA-256 hashes.

Trade API

:8085

Spring Boot · MyBatis · Java 21

Accounts, positions, orders. Trusts tokens by verifying signature and issuer only — the two services never call each other over the network.

Executor

:8083

Spring Boot · Java 21

Consumes order events, calls the quote provider, fills or rejects with an optimistic lock on cash balance, and hosts the analytics ETL subprocess.

PostgreSQL

:5432

PostgreSQL 16

One database, two schemas: auth for users and refresh tokens, trading for accounts, holdings, orders and instruments.

Kafka

:9092

Apache Kafka 3.8 · KRaft

Three topics keyed for ordering guarantees, each with a paired dead-letter topic. Auto-creation is off so a missing topic fails loudly.

Containerization notes. JWT_SECRET and JWT_ISSUER must be identical across Auth Service and Trade API. The Auth Service's RSA keypair (login-keys/) and analytics.duckdb both need volumes that outlive a container restart. Kafka's topics must be created explicitly before the Trade API or Executor start producing/consuming, since auto-creation is disabled by design.
